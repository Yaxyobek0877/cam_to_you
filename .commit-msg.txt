fix(v0.1.13): CUDA hwaccel for NVENC + auto-restart + sub-stream recommendation

Investigated camera disconnect issue extensively. Findings:

EVIDENCE collected via real Hikvision camera testing:
- -c copy -an: runs 45+ sec without disconnect ✓
- NVENC + CUDA + no audio: 30 sec ✓
- NVENC + audio (any preset): 5-15 sec then RTSP EOF ✗
- libopenh264/x264: even worse (CPU too slow for HEVC decode)

ROOT CAUSE:
NVENC H.264 encoding of HEVC source on RTX 3060 was running at
~0.86x realtime with SOFTWARE decode (CPU bottleneck on HEVC).
This made FFmpeg lag behind camera, RTSP buffer overflowed,
camera closed connection.

FIX 1: Hardware-accelerated decode for NVENC
- Added -hwaccel cuda -hwaccel_output_format cuda when using NVENC
- HEVC decode now runs on GPU (NVDEC), end-to-end on GPU
- Encoding speed went from 0.86x to 1.03x+ realtime

FIX 2: NVENC preset p4 → p1 (fastest)
- More headroom above realtime requirement
- Quality difference negligible at live streaming bitrates

FIX 3: Removed flags that didn't help
- -fflags +discardcorrupt (was dropping frames)
- -thread_queue_size 4096 (no effect)
- -user_agent, -reorder_queue_size (no effect)
- -vf format=yuv420p (incompatible with CUDA path)

FIX 4: Manager restart logic (already in v0.1.12)
- Restart on any FFmpeg exit, not just errors
- Reduced delay from 5s to 2s for first 5 retries

KNOWN LIMITATION: audio re-encoding (PCM mu-law → AAC) can still
cause periodic camera disconnects. Auto-restart mitigates this
(2 sec gaps) but YouTube might end broadcast on many quick reconnects.

UI: Strong recommendation banner in Stream form when encoder != "copy"
- Explains HEVC → H.264 transcoding risk
- Step-by-step guide to enable sub-stream + copy combo
- "Sub-stream + Copy" = camera sends H.264 directly, 0% CPU,
  100% reliable

For maximum reliability on Hikvision/HEVC cameras:
1. Enable sub-stream in camera (Cameras page → edit → toggle)
2. Select "Copy" encoder in stream config
3. Result: direct pass-through, no transcoding, no disconnects
